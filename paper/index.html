Prioritizing Content Refresh: a client-heldout model that ranks pages at risk of meaningful click decline

A decision-support research paper · built on the FlyRank pseudonymized search-intelligence warehouse · September 2026

Abstract

We ask which content items a limited editorial team should review first to catch pages that are about to lose clicks. We aggregate February 2026 search and engagement signals plus static content metadata from the FlyRank warehouse into one row per page, and train a random forest to rank each page's probability of meaningful click decline over the following month (March 2026), validated with a client-holdout split so no client's pages appear in both train and test. Against a transparent hand-written rule (stale + visible + weak-position + low-CTR), the model scores higher on area-under-curve and on precision@50 for the held-out clients. The result is a ranked, reason-coded action queue — a prioritization aid, not a causal claim that a refresh will recover a page.

1.Introduction / problem statement

The decision this work supports is simple to state and expensive to get wrong: when an editor has capacity to review 50 pages this week, which 50 should they open first? The unit of analysis is one content item (page) for one pseudonymized client. The output is a score per page that orders a review queue. The human action is manual review — then refresh, expand, protect, monitor, or prune the page.

The cost of a wrong call runs both ways: reviewing a healthy page wastes editorial time, while skipping a quietly-declining page lets a real visibility loss compound. A fixed rule can catch the obvious cases (a page that is both stale and high-traffic), but the decision depends on interactions — volume, position, click-through rate, freshness, and content depth move together in ways a hand-written threshold misses. A learned ranking can weigh those interactions, which is exactly the space where machine learning earns its keep over a static rule.

2.Data

We use the FlyRank internship warehouse release (FlyRank/internship-warehouse, build flyrank_pseudonymized_warehouse_release_v20260703), a gated, pseudonymized snapshot hosted on Hugging Face. Two tables are joined:

Windows. Feature window = February 1–28, 2026. Label window = March 1–31, 2026. Features are aggregated only from the February partition; the March partition contributes only the label aggregate (total clicks).

Exclusions and why.

  • Client names, domains, URLs, queries, titles: not present in the release — everything is pseudonymized (client_hash_id, content_hash_id).
  • trend_direction / trend_pct: derived from the same comparison we predict; using them would leak the answer.
  • Rows with gsc_data_available = FALSE: no usable search signal.
  • Pages with fewer than 5 February clicks: too little signal to distinguish decline from noise (a deliberate minimum-volume filter).
  • The 90-day query table: its window overlaps the label month, so we leave it out entirely rather than risk leakage.

After filters the modeled set is 21,954 pages across 31 pseudonymized clients.

3.Methodology

Label

The target is a future, observed outcome: is_declining = 1 when a page's March clicks fall to ≤ 70% of its February clicks (a ≥30% drop), and the page had ≥ 5 February clicks. This is a proxy for "worth a refresh review" — a page that meaningfully lost clicks in the next month. The base rate of decline on the held-out set is 0.261.

Features (all known before March 1)

From February: impressions, clicks, CTR, average position, sessions, engagement rate, active days, days-with-impressions (log-transformed for the heavy-tailed totals). From dim_content: word/character count, content age, days since last update, content type, and search intent. IDs are used for grouping and splitting only, never as features.

Baseline

A transparent weighted rule: 0.35·visibility + 0.30·staleness + 0.20·weak-position + 0.15·low-CTR, each term a percentile rank of a February signal. It encodes the same "stale but visible, poorly positioned, under-clicking" intuition the model is asked to beat.

Validation

Client-holdout split (GroupShuffleSplit): ~80% of clients train, ~20% held out (7 clients, 12,145 pages). This is the honest design for this data — pages from the same client share structure, and a random row split would let the model peek at a client it effectively already saw. Because the review queue is used top-K, we report precision@K alongside area-under-curve and average precision, always next to the base rate.

Leakage audit

No March column enters any feature. No trend field. IDs are grouping-only. The query table is excluded. Every feature is computable from information available at February 28.

On held-out clients the random forest reaches precision@50 ≈ 0.560 versus 0.200 for the baseline (≈2.80× lift) and a higher AUC. The precision@K curve shows the gap persists across review capacities, not just at one lucky K. The logistic regression sits right alongside the forest — a robustness sign, not a weakness: the signal is largely linear in the transformed features. AUC is modest (≈0.61), but the precision@K lift is the number that matters for a review queue: the model surfaces nearly 3× more genuinely-declining pages in its top 50 than the rule. Predicting a future outcome across unseen clients is genuinely hard; the value here is the ordering and the reason codes, not a headline accuracy number.

The strongest drivers are volume and position signals plus content age — the model is picking up a real "visible, aging, slipping" profile rather than a single magic column.

5.Limitations & honest framing

Everything here is observational. We measured an association between February signals and March outcomes; we did not run an experiment, so we cannot claim a refresh causes recovery. "Decline" is a proxy for "worth reviewing", not proof a page is broken. A single February→March pair may carry seasonality; nine of seventy clients have enough history for seasonality checks, and the rest do not. The 30% threshold and the 5-click floor are policy choices, not facts — different teams should re-tune them to their own review capacity (see the guide's threshold section). The label misses consolidation (a sibling page absorbing demand) and SERP-level changes, which look like decline to this model. Use the queue as a decision-support list to route human review, never as an auto-publish signal.

Starter cross-check. Independently of the warehouse result, the bundled 30,000-row starter slice reproduces the same finding with its own client-holdout split: a random forest reaches precision@50 ≈ 0.64 versus ≈ 0.30 for the rule baseline (~2× lift). Both datasets agree that a learned ranking beats a fixed rule at surfacing declining pages — and the warehouse result is the harder, more honest test, because it predicts a *future* outcome across unseen clients rather than classifying a current trend bucket.

6.Ranked recommendations

The queue ranks every modeled page by predicted decline probability. Each row carries a reason code (why it scored high) and a suggested action (what an editor might do). The mapping:

  • refresh high decline-risk and stale → oldest, riskiest pages first
  • refresh_review high decline-risk → verify, then act
  • expand thin + high-volume → depth gap with demand behind it
  • review_ctr low CTR + high volume → metadata/title/snippet review
  • monitor everything else → revisit next cycle

Reason codes: OLD (≥365 days old), LOW_CTR, WEAK_POSITION (>20), HIGH_VOLUME, THIN_CONTENT (<1200 words), HIGH_DECLINE_RISK (model ≥0.65). Top of the queue:

7.Reproducibility

Everything is deterministic (seed 42, fixed build, fixed windows). To re-run:

  1. hf auth login (read token; the gated dataset needs access).
  2. python work/capstone_analysis_warehouse.py → writes work/outputs/warehouse_results.json and the queue.
  3. python work/capstone_analysis_starter.py → starter cross-check.
  4. python work/build_paper.py → regenerates this page from those artifacts.

Notebooks live in work/notebooks/; the full history of weekly assignments is in work/. Repo: github.com/PREK-X/flyrank-internship. Environment: Python 3.14, duckdb, scikit-learn, pandas, numpy, matplotlib (requirements.txt).
